\section{The commit model}
\label{sec:model}

The first educational objective is Git's data model: commits as snapshots
of the whole tree, linked into a graph; history as that graph, not as a
sequence of diffs.

\subsection{Documented misconceptions and difficulties}

Learners' challenges with Git's conceptual model are documented from course
surveys and teaching observations \autocite{IsomottonenCochez2014}, and
Git's own concepts have been shown to misfit their purposes in analysable
ways \autocite{DeRossoJackson2016Gitless}.
Repository-data analysis of students' Git use sharpens the picture for the
commit model in particular: across three courses, students
\textcquote{Cochez2013DVCSUsage}{regard the version control system as file
storage}, committing too rarely and writing meaningless commit
messages---the commit-as-save conflation read off the repositories rather
than from self-report.
That the difficulty is intrinsic to Git and not merely a novice's
inexperience is corroborated at scale: a study of 80\,370 Stack Overflow
questions finds that even practising developers
\textcquote{Yang2022GitCommands}{frequently face difficulties when using
various Git commands}.
\Textcite{IsomottonenCochez2014} trace such difficulties to a missing mental
model---\textcquote[Sec.~5.7]{IsomottonenCochez2014}{The absence of a proper
mental model seems to cause the blind-testing effect}, in which learners
\enquote{just try them out} instead of reasoning about the commands.

\subsection{Candidate critical aspects}
\label{sec:model-aspects}

Reading the difficulties above for the aspect the learner had not
discerned gives three candidates.
The literature on Git is richer than on the shell but still thin on
learners' own conceptions (\cref{sec:protocol-measurement}), so we say
for each what it rests on: a documented difficulty, an observation from
our own course, or the structure of the object of learning itself.

\begin{description}
  \item[A commit is a snapshot, not a diff]
    Each commit contains the whole tree as it stood; the difference is
    computed when asked for, not stored.
    No study documents the opposite conception; the aspect is posited
    from the object of learning, where it is the first thing the
    notional machine of \cref{sec:background} has to get right.
    Tested by the item \emph{what a commit keeps}
    (\cref{app:knowledge-items}), asked closed at the end only, and by
    its open twin \emph{what Git has kept} (\cref{app:open-items}) at
    both administrations.
  \item[History is a graph]
    Commits point at their parents; nothing is a \enquote{folder of
    versions}.
    This is read off the repository-data finding that students
    \textcquote{Cochez2013DVCSUsage}{regard the version control system
    as file storage}: a store of files has versions side by side, a
    history has them linked.
    Tested by the item \emph{where earlier versions live}; the open item
    \emph{explaining a history} shows the graph itself and asks what it
    shows.
  \item[Nothing happens without a commit]
    Saving a file and recording a version are different acts.
    Read off the same repository data: students who commit too rarely
    and write meaningless messages \autocite{Cochez2013DVCSUsage} are
    treating the save as the record and the commit as a formality.
    Tested by the item \emph{after you save}.
\end{description}

None of the three rests on a learner's own account of a commit, because
none has been collected (\cref{app:protocol}); the open accounts of
\cref{sec:method-instruments} are where one would first show.

\subsection{Patterns of variation}

\begin{itemize}
  \item Contrast (recorded vs not): edit a file, observe
    \texttt{git status}/\texttt{git log} before and after
    \texttt{git commit}.
  \item Generalisation (commit invariant, content varies): commits
    recording one file, many files, a deletion---always the same kind of
    object, shown by \texttt{git show}.
  \item Fusion: follow \texttt{git log --graph} while making a small
    history with a merge.
\end{itemize}
